## Что должно получиться

Пользователь просит список животных. Агент находит подходящее правило из `data/lists.csv`, уточняет только недостающие существенные параметры, выполняет правило на разрешённых фермах и показывает результат справа. Фильтры, колонки и данные в таблице соответствуют выполненному правилу. Пользователь может продолжить работу с этим представлением вручную.

| Было | Должно стать |
|---|---|
| CSV — отдельный файл с названиями и текстовыми настройками | Версионируемый каталог исполняемых определений списков |
| Агент знает ограниченный набор полей и сам собирает фильтры | Агент выбирает конкретное определение, читает его условия и передаёт параметры |
| Событийная БД покрывает основные семейства фактов, но не все поля CSV | Для каждого используемого поля определены источник значения, тип, единица, временная область и тестовые данные |
| Есть проверки отдельных выборок | Есть проверка каждой из 6 735 записей источника и сквозные проверки выбора правил агентом |

Цель — весь переданный каталог, а не только популярные списки. Поддержка каталога не означает поддержку любого будущего названия поля или неизвестной формулы.

## Границы

Входят обычные списки и выполнение условий календарных списков по запросу пользователя, включая вложенные **И / ИЛИ / НЕ**, колонки, `vitality_filter`, параметры, вычисляемые поля и совместимое представление группировок.

Не входят автоматический запуск по расписанию, уведомления, рабочие списки с вводом данных, запись животноводческих операций агентом, новое оформление приложения и production-развёртывание. `run_type` и `interval_text` сохраняются без потерь как метаданные. Запрос «на сегодня» фиксирует дату расчёта, но не создаёт расписание.

Существующее деление сохраняется: `arka_test` хранит факты и определения полей; продуктовая БД хранит чаты, каталог правил и `ReportView`. Отдельные базы для классов событий не создаются.

## 1. Каталог определений списков

Ниже — логический контракт. Физические `RuleSourceSnapshot`, `RuleDefinition`, `RuleBinding` созданы миграцией продуктовой БД `0009_condemned_sway.sql`.

| Сущность | Содержимое и обязательные атрибуты |
|---|---|
| `RuleSourceSnapshot` | ID, имя источника, SHA-256, версия формата, дата импорта, число записей |
| `RuleDefinition` | Snapshot ID, `company_id`, `list_id`, версия; все 18 исходных колонок без потерь; исходный текст и его разобранное представление |
| `RuleParameter` | ID, имя, тип, единица/справочник, обязательность, допустимые значения, источник значения по умолчанию, места использования |
| `RuleBinding` | Версия правила, доступная ферма стенда, соответствия полей и справочных значений, область применимости и версия сопоставления |
| `RuleValidation` | Результаты разбора, семантической проверки, сопоставления, данных, SQL и отображения; коды проблем с точной ссылкой на фрагмент источника |
| Привязка к `ReportView` | ID и версия исходного правила, версия binding, связанные параметры, дата расчёта, отпечаток плана, признак ручного изменения |

Ключ определения — `(snapshot_id, company_id, list_id)`. Одинаковые названия не объединяются. Повторный импорт того же snapshot не создаёт дубли; новый снимок не перезаписывает использованную версию. Общие вычисления можно переиспользовать, но происхождение каждой записи сохраняется.

`company_id` — идентификатор источника, а `farm_id` — идентификатор данных и доступа стенда. Их равенство не предполагается. Для тестового воспроизведения правила явно связываются с одной или несколькими из шести синтетических ферм. Справочные номера групп, статусов, схем, быков и сотрудников переводятся через таблицу соответствий; «похожее название» само по себе не является подтверждённым соответствием.

Исходные тексты конфиденциальны и считаются данными, а не инструкциями модели. Каталог доступен только через сервер и проверенные bindings. Недоступное правило не должно раскрываться через поиск, название или диагностическое сообщение.

## 2. Разбор и смысл правил

CSV читается CSV-парсером. Текст условий разбирается отдельным детерминированным парсером: он обрабатывает реальные и экранированные переводы строк, отступы, скобки, названия групп, операторы и значения, сохраняя связь каждого узла с исходным текстом. Нельзя разбирать весь CSV разделением на строки или поручать LLM окончательное определение логики.

Каноническая модель разделяет:

- **условие отбора**: дерево групп `AND / OR / NOT` и типизированных сравнений;
- **операнды**: константа, значение параметра, ссылка на другое поле, дата относительно момента расчёта;
- **определение поля**: способ получить значение из фактов или вычислить его;
- **выдачу**: упорядоченные колонки, группировку и, если подтверждены источником, именованные сегменты;
- **область**: разрешённые фермы, жизненное состояние, дата и версия данных.

| Конструкция | Контракт |
|---|---|
| `AND / OR / NOT` | Сохраняются вложенность, отрицания и порядок исходных узлов; упрощение допускается только с доказанным равенством результата |
| Числа и диапазоны | Тип и единица определены; различаются строгие и включительные границы; десятичные значения не теряют точность |
| Пустые значения | `NULL`, пустая строка, ноль и `false` различаются; отрицание не превращает отсутствие факта в положительный факт |
| Даты | Один `as_of` на запуск; календарные дни считаются в часовом поясе каждой фермы; относительные даты не являются фоновым расписанием |
| Сравнение полей | Справа может быть типизированная ссылка на поле, а не только строковый литерал; типы и единицы должны быть совместимы |
| Параметры | Незаданный обязательный параметр блокирует запуск; модель не выбирает случайный порог |
| Справочники | Используются устойчивые ID и версия binding, а не поиск совпадающих подписей во время SQL-запроса |
| Отсутствующие фильтры | Означают отсутствие условий только после проверки экспорта; `vitality_filter` и доступ всё равно применяются |
| Именованные блоки | Их объединение и членство животного в нескольких блоках выясняются отдельно; несколько корней не склеиваются молча через `AND` или `OR` |
| Ошибка/неизвестное поле | Конкретная причина и исходный фрагмент; запрещены удаление условия, замена ближайшим полем и запуск ослабленного правила |

Политика `NULL` фиксируется таблицами истинности и проверками. Если поведение оригинальной системы не следует из материалов, соответствующее решение отмечается в реестре вопросов; нельзя заявлять точное совпадение с источником до его разрешения.

Ограничения глубины, числа условий, значений и колонок пересматриваются по полному корпусу. Прежние пределы 30 условий и 30 колонок увеличены до 128 и 64; глубина остаётся 8. Ограничение пакета ручных операций не обрезает применение целого правила. Ресурсные пределы остаются, но импортированное правило не обрезается ради прохождения валидации.

## 3. Подготовка базы данных

Базовые объекты остаются прежними: **ферма → животное → история событий**. Расширяются справочники, детали событий и вычисления, которые нужны фактическому каталогу. Определения списков не помещаются в историю животных.

### Единый реестр полей

Развивается существующий `field_definition`, а не создаётся второй независимый словарь. Для каждого используемого поля обязательны:

| Группа атрибутов | Что фиксируем |
|---|---|
| Идентичность | Канонический код, версия, исходные названия и ферменные псевдонимы |
| Значение | Тип, единица, справочник, допустимые операторы, значение отсутствия |
| Происхождение | Атрибут животного, тип события/деталь, пользовательское значение, внешняя оценка или вычисление |
| Время | Текущая/предыдущая лактация, весь срок жизни, окно дат, первое/последнее/n-е событие, `occurred_at` и `recorded_at` |
| Вычисление | Формула и версия, зависимости, параметры фермы, правило округления, дата актуальности |
| Представление | Подпись, формат, возможность фильтрации, сортировки, колонки и группировки |
| Проверка | Правила CSV, которые используют поле; эталонные значения; состояние готовности |

API, агент, SQL-компилятор и UI получают разрешённые возможности из этого реестра. Клиенту и модели не передаются SQL-фрагменты. История изменений реестра не должна молча менять ранее открытое правило.

### Исполнение формул

Сейчас системные seed-формулы используют операции `date_diff`, `count`, `add_rule`, `subtract_rule`, а `evaluate_formula_ast` — другую грамматику (`DAYS_BETWEEN`, `COUNT_EVENTS`, `ADD_DURATION` и др.). `field_value_at` отдельно обрабатывает восемь кодов и затем пользовательские значения; наличие записи в `calculated_field` не включает её автоматически в запрос.

Нужны единая версия грамматики, миграция существующих определений и проверяемое исполнение зависимостей. Обязательны контроль циклов, совместимость типов, предел стоимости, корректная обработка `NULL`, стабильный порядок событий с одинаковым временем и точная область лактации. Источник формул и параметров должен быть одинаковым для таблицы и агента.

### Когда оригинальный расчёт отсутствует

Если CSV содержит только название показателя, например прогноз 305M, его оригинальную методику нельзя восстановить из названия. Для проверки отбора на стенде допускается детерминированно сгенерированный результат внешней оценки с датой, единицей и происхождением `SIMULATION`; это входное значение правила, а не заявление о воспроизведении методики заказчика.

Раздельно учитываются **точность исполнения условий** и **происхождение значений полей**: исходный факт, вычисление по известной формуле, тестовое значение внешней оценки, неразрешённое определение. Неизвестные условия самого правила подменять тестовым предположением нельзя. В пользовательскую таблицу не добавляются служебные предупреждения в каждой строке; происхождение хранится в метаданных и отчёте проверки.

### Данные и производительность

Основной набор 6 × 8 500 животных сохраняется. Для отсутствующих фактов добавляется воспроизводимая история с теми же животными и связями. `db-reset.sh`, `db-check.sh` и `db-generate-scale.sh` пересоздают данные: их нельзя использовать как способ незаметно обновить текущий стенд.

Проверочные мини-наборы живут отдельно от основного нагрузочного набора. Для каждого правила нужны ожидаемые ID животных, значения колонок и причины включения/исключения. Проверяются границы, отсутствующие события, несколько лактаций, отменённые/исправленные события, повторные протоколы и временные переходы. Пустой результат на случайном наборе не доказывает корректность.

Вычисления общего пользования выполняются пакетно, индексируются и переиспользуются. Запрещён отдельный полный проход по истории для каждой ячейки каждой строки. Проекция `animal_state_query` остаётся производной; она хранит версию данных и расчёта. Смена локальной даты должна актуализировать относительные показатели при чтении/обновлении проекции, даже если новых событий не появилось. Обновление проекции не является запуском календарного списка.

## 4. Как агент выбирает и выполняет правило

1. Сервер получает пользователя, разрешённые фермы и актуальные `viewId/revision`. Снятый фильтр фермы означает все разрешённые фермы; правило одной компании не переносится на остальные автоматически.
2. Агент ищет кандидатов по намерению, названию, описанию и проверенным синонимам. Поиск ограничен доступными bindings; частота запуска — вспомогательный признак, а не доказательство смысла.
3. Агент читает полное определение кандидата: условия, область, параметры и готовность. Одного совпавшего названия недостаточно.
4. При нескольких разных правилах задаёт короткий вопрос о существенном различии. При отсутствии правила сообщает это; произвольный набор фильтров допустим отдельным пользовательским запросом, но не выдаётся за правило из CSV.
5. Сервер связывает параметры, разрешает поля и справочники, фиксирует версию правила, дату расчёта и версию данных. Любая неразрешённая зависимость останавливает применение до изменения view.
6. Сервер создаёт безопасный план запроса и атомарно меняет представление через существующий View service с проверкой revision. Изменение отправляется в UI через `data-view-state`.
7. Таблица и ответ агента используют один план и снимок. Агент называет применённое правило, количество животных и существенные условия. Ручная правка делает view изменённой копией правила, не меняя исходный каталог.

Предлагаемые новые tools:

| Инструмент | Вход | Выход и ограничения |
|---|---|---|
| `searchListRules` | Текст намерения, необязательные сужения поиска | Краткие разрешённые кандидаты с ID, версиями, назначением и существенными различиями; не весь CSV |
| `getListRule` | ID и версия кандидата | Полные условия, параметры, колонки, bindings, нерешённые зависимости |
| `applyListRule` | Правило и версия, параметры, целевой view и ожидаемая revision | Валидированное новое состояние и идентификатор выполнения; никаких SQL или произвольного назначения прав |

`queryAnimals`, `summarizeAnimals`, `getViewState`, `updateView` остаются общими инструментами. Их данные должны соответствовать применённому плану. Названия новых tools проектные; сейчас таких инструментов нет.

### Контрольный пример: список 541

Для правила `(company_id=20, list_id=541)` обязательны исходный отбор `Живые` и полное дерево:

```text
(
  дней на пресинге = 36
  И (статус = Новотельная ИЛИ статус = Готова к осеменению)
)
ИЛИ
(
  дни с осеменения >= 42
  И дни с осеменения <= 48
  И (статус = Готова к осеменению ИЛИ статус = Новотельная)
)
```

Это пример конкретного определения, а не универсальная формула для всех ферм. Подмена дерева единственным `status = READY_FOR_INSEMINATION` запрещена. Если запрос не позволяет выбрать между этим и другим списком осеменения, агент уточняет выбор; если выбран этот список, значения 36, 42 и 48 берутся из источника.

## 5. Правая таблица и совместимость

Сохраняются компактная строка чипов, создание фильтра из неё, рядовой съёмный фильтр фермы, одно поле группировки, закреплённый номер животного, карточка `Sheet`, размеры панелей 46 px и единые структурные линии. Отдельный «расширенный фильтр» не возвращается.

Дерево отбора и визуальная вложенность групп таблицы — разные вещи. Полные условия обязаны сохраняться и отображаться без потери смысла; это не требует многоуровневых строк группировки. Локальное отображение v5 само по себе ещё не даёт ручного создания произвольных групп **И / ИЛИ / НЕ** — такую возможность нельзя отмечать готовой без проверки.

Если правило содержит несколько полей группировки или именованные сегменты, его условия и членство в сегментах не теряются. Предпочтительная совместимая форма — один составной ключ/метка сегмента и необходимые колонки. Допустимость такой формы, поведение пересечений и подсчёт уникальных животных подтверждаются на реальных определениях. До подтверждения соответствующее представление имеет открытый разрыв; молчаливое удаление группировки не считается покрытием.

При применении правила явно определяются заменяемые части view: фильтры и колонки правила заменяют соответствующие части; отдельный пользовательский фильтр фермы сохраняется только при совместимости с binding, иначе требуется выбор области. Настройки ширины, состояния оболочки и файлового просмотра не затрагиваются. Конфликт revision не перезаписывает ручные изменения.

## 6. Доказательство готовности

Для каждой исходной записи ведутся отдельные признаки: **импортирована → разобрана → смысл определён → поля сопоставлены → данные подготовлены → запрос проверен → отображение проверено**. Отдельно проверяется выбор правила по естественному языку. Пройденный парсер не даёт права написать «список работает».

Реестр покрытия содержит исходный ключ, версии, используемые поля и операторы, параметры, источники значений, блокирующие причины, ссылки на эталонные проверки, результаты и отображение. Все 6 735 записей входят в знаменатель; дублирующиеся формулы и редкие списки не исключаются из отчёта.

Полная готовность означает: каждое правило имеет проверяемую семантику, выполняется целиком и выводит правильные ID/колонки/группы; число нерешённых зависимостей равно нулю. Для несовместимых или противоречивых исходных условий фиксируется доказанный пустой результат, а не придумываются подходящие животные. Вариант только с частью правил обозначается частичным результатом и не закрывает цель.

Приёмка охватывает доступ между фермами, отсутствие SQL и prompt injection из исходных строк, параметры и типы, границы дат и чисел, версии формул, отсутствие дублей между страницами, согласованность count/строк/групп, конкурентные ручные правки и работу реальной подключённой LLM. Полный план проверок и порядок поставки — [CSV-RULES-PLAN.md](CSV-RULES-PLAN.md).
